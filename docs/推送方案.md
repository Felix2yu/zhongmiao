# ntfy 后台推送方案

> 状态：待实施。本文档由 2026-10-26 的问题排查整理而来，可直接按章节逐项实施。

## 背景与现状问题

### 问题一：前台静置收不到

ntfy 通道是**纯轮询**（`FeedClients.fetchNtfy` → `GET /{topic}/json?poll=1&since=游标`），没有常驻连接，而同步只在以下时刻触发：

- 冷启动（`bootstrap` → `syncNow("启动")`）
- `scenePhase` 变为 active（离开再回到应用那一刻，ZhongmiaoApp.swift）
- 订阅动作当时（`subscribeNtfyTopic`，此刻测试消息多半还没发）
- 手动刷新 / 下拉刷新、网络重连、iOS BGTask（仅 iOS，20 分钟一次，尽力而为）

应用保持前台静置时**没有任何定时器去轮询**，测试通知永远不会被拉取。前台的横幅展示本身没问题（`NotificationDelegate.willPresent` 已返回 `.banner`），只是没机会被触发。

### 问题二：后台/退出后收不到

iOS 应用挂起后进程冻结，BGAppRefresh 不可靠且延迟不可控；macOS 进程虽存活但同样没有轮询循环。文档 `docs/NOTIFICATIONS.md` 已写明：「App 被杀死也要立刻收到，只有 APNs 中继这一条路」。

而中继（`server/push-relay`）目前是**被动模型**：服务端 `POST /v1/events` 才有事件，它不认识 ntfy，也没有订阅概念。ntfy 主题的消息没有任何路径能变成 APNs 推送。

### 现有基础设施盘点

- 中继已具备：设备注册（`POST /v1/devices`）、事件存储与幂等（JSON 文件，`Event.Key()` 去重，7 天 TTL）、全设备 fanout（alert 载荷，`service/url/eventID` 自定义字段）、`GET /v1/events?service=&since=` 回补接口、APNs p8 token 认证 + 失败重试 + 410 清理设备。
- 应用已具备：三通道轮询引擎（feed / ntfy / relay，各自独立游标）、统一去重账本、前台补发、APNs token 上报（`uploadPushToken`）。
- 拓扑：ntfy 与 zm-push 同机同 Docker network，中继直连 `http://ntfy:80` 零成本；Nginx 已对 ntfy 关闭缓冲支持长连接。
- 缺口：无 entitlements（`aps-environment`）；`didReceiveRemoteNotification` 未实现（alert 推送不需要，暂不补）；APNs 载荷用 `service` 字段而本地点击回跳读 `serviceID`，字段名不统一。
- 去重键已对齐：中继回补走 `FeedEntry`，`makeID(serviceID, eventID)`——只要中继把 ntfy 消息 id 原样放进 `Event.ID`，推送、轮询、回补三条通道共用同一份账本，不会重复展示。

## 目标

1. ntfy 主题的新消息在应用**前台、后台、被杀死**三种状态下都能收到（前两者由中继 APNs 秒级送达，前台另有轮询兜底）。
2. 应用侧订阅关系自动同步到中继，无需手工维护服务端配置。
3. 去重不破坏：同一条消息在轮询、推送、回补三条通道里只入库、只弹一次。

## 方案总览

```
ntfy 主题消息 ──流式订阅──▶ push-relay watcher
                              ├─ 存事件（幂等：Service|id:<ntfy-id>）
                              └─ fanout APNs alert ──▶ 系统直接展示（应用可死）
应用订阅/取消订阅 ──POST/DELETE /v1/subscriptions──▶ 中继（watcher 重建连接）
应用下次同步 ──GET /v1/events?service=ntfy:<topic>&since=游标──▶ 回补收件箱（与推送去重）
应用本地 30s 轮询 ──▶ 前台兜底（macOS 后台进程存活期间也跑）
```

## 服务端改动（server/push-relay）

### store.go

- `persisted` 增加 `Subscriptions []Subscription`，结构 `{Topic, Service}`，按 topic 唯一。
- 新增 Upsert / Remove / List 订阅方法，沿用现有 JSON 文件 + tmp 原子替换的存储方式。

### ntfy.go（新文件）—— watcher

- 配置：`ZM_NTFY_BASE_URL`（如 `http://ntfy:80`）、可选 `ZM_NTFY_TOKEN`（自建 ntfy 开访问控制时读取所需的令牌）。未配置则不启动 watcher，行为与现在完全一致。
- 一条常驻连接订阅全部主题：`GET {base}/{topic1,topic2}/json?since=<上次处理时间>`，`bufio.Scanner` 逐行解析。
- `event=="message"` 转成事件入库并 fanout：
  - `ID` = ntfy 消息 id（去重关键，不可改动）
  - `Service` = 订阅映射的 service（独立主题为 `ntfy:<topic>`，单服务主题为服务 id）
  - `Title` = title，缺省用 topic；`Body` = message
  - `CreatedAt` = `time.Unix(msg.time)`
  - `Priority`：ntfy 1 → `passive`，≥4 → `time-sensitive`，其余 `active`（镜像应用端 `NotificationItem.fromNtfy`）
  - `URL` = click
- 连接管理：
  - 订阅集合变化时重建连接；
  - 断线按指数退避重连（1s → 60s 封顶），重连带 `since` 补缺口；
  - 看门狗：超过 3 分钟没有收到任何行（ntfy keepalive 约 45s 一次）强制重连；
  - **首次连接用 `since=<now>`**，避免把服务器缓存的历史消息炸成推送风暴。

### main.go

- 新增鉴权端点（走现有 `X-Zhongmiao-Token` 中间件）：
  - `GET /v1/subscriptions` → `{"subscriptions":[{"topic":"alerts","service":"ntfy:alerts"}]}`
  - `POST /v1/subscriptions`，body `{"topic":"alerts","service":"ntfy:alerts"}`（service 缺省 `ntfy:<topic>`），按 topic upsert
  - `DELETE /v1/subscriptions/{topic}`
- 启动 watcher，订阅变化时通知其重建连接。

### apns.go

- payload 增加 `"serviceID": e.Service`（与现有 `service` 并存，不破坏兼容）——修复点击推送后 `NotificationDelegate.didReceive` 读 `info["serviceID"]` 拿不到值、无法跳转的问题。

### deploy/README.md

- compose 片段补环境变量：`ZM_NTFY_BASE_URL=http://ntfy:80`、`ZM_NTFY_TOKEN`（可选）。

## 应用端改动（Sources/）

### AppModel.swift

1. **buildTargets()**：有 `ntfyTopic` 的 target（独立主题 + 单服务主题）补上 `relayURL` / `relaySecret`，让引擎的 relay 回补通道覆盖它们。`NotificationEngine` 本来就独立拉 relay 通道（feed / ntfy / relay 三者互不排斥），无需改动引擎。
2. **订阅同步** `syncNtfySubscriptionsToRelay()`：
   - 期望集合 = 独立主题（service=`ntfy:<topic>`）∪ 启用了通知且配了 `ntfyTopic` 的服务（service=服务 id）。
   - bootstrap 时 `GET /v1/subscriptions` 补差：**只增不删**（避免多设备互删对方的订阅）。
   - 触发点：`subscribeNtfyTopic` / `unsubscribeNtfyTopic` / `updateSettings`（服务 ntfyTopic、通知开关、中继地址密钥变更）。
   - 中继未配置时记日志跳过，不报错打扰。
3. **周期同步循环**：`activate()` 里起 Task 循环，每 30s `syncNow(reason: "周期")`。
   - iOS：仅 `scenePhase == .active` 时执行（后台交给 APNs + BGTask）；
   - macOS：进程存活即执行（SwiftUI 默认关窗不退出，窗口关着也能收）。
   - AppModel 增加 `sceneIsActive` 状态，由 ZhongmiaoApp 的 onChange 和 MacAppDelegate 写入。
4. **subscribeNtfyTopic**：ntfy 地址未解析时返回错误文案，不再静默订阅失效（现状：`buildTargets` 里 `if let ntfyBase` 会把没地址的订阅悄悄排除）。

### FeedClients.swift

新增三个方法（复用 `withRetry` 与 `X-Zhongmiao-Token` 头）：

- `registerNtfyTopic(relay:secret:topic:service:)` → `POST /v1/subscriptions`
- `unregisterNtfyTopic(relay:secret:topic:)` → `DELETE /v1/subscriptions/{topic}`
- `fetchNtfySubscriptions(relay:secret:)` → `GET /v1/subscriptions`

### SettingsView.swift

「推送中继」区块显示主题推送状态：已注册 N 个主题 / 同步失败原因（与现有 `pushError` 展示并列），让链路是否通一眼可见。

### project.yml + Config/

- 新增 iOS / macOS 两个 entitlements 文件，声明 `aps-environment`（development），挂到对应 target 的 `CODE_SIGN_ENTITLEMENTS`。不加的话真机签名后拿不到 device token。
- 本机 `CODE_SIGNING_ALLOWED=NO` 构建不受影响；真机推送需要正式签名 + 中继配好 APNs p8，调试期中继用 `ZM_APNS_ENV=development`。

## 顺手修

- `NtfyStreamDecoder.sinceParameter`：注释写「向上取整」但代码是 `.rounded(.down)`。向下取整是安全方向（多拉不漏），改注释即可。

## 明确不做

- **应用侧 ntfy 读鉴权**：`fetchNtfy` 仍不带凭据，服务器若 deny-all 需放行只读；要支持令牌另立任务。
- **取消订阅的多设备协调**：只有显式 unsubscribe 才从服务器删订阅，bootstrap 补差只增不删。
- **BGTask 策略不动**：仍是尽力而为的兜底，不指望它实时。
- **`didReceiveRemoteNotification` 不实现**：alert 推送由系统直接展示，不需要后台处理回调。

## 验证

1. `cd Packages/ZhongmiaoCore && swift test`（现有 47 个用例 + 给订阅同步的 URL 拼装/集合差分补测试）
2. `cd server/push-relay && go vet ./... && go build ./...`
3. 双端 `xcodebuild` 编译（照 README 命令：iOS 模拟器 SDK + macOS）
4. 手动链路（部署后）：
   - 应用订阅主题 → `curl -d "test" https://ntfy.<域名>/<主题>` → 秒收 APNs 推送；
   - 应用挂起/杀掉状态下发消息 → 系统展示推送；重开应用 → 收件箱经 `/v1/events` 回补该消息，且不重复弹；
   - 取消订阅 → 中继 `GET /v1/subscriptions` 确认已删，再发消息不再推送。
